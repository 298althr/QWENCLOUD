2. What Is Working (Implemented and Verified)

Qwen AI integration - DashScope API with model rotation (qwen-turbo, qwen-plus, qwen-max), token tracking, budget enforcement, kill switch, guardrails with caching and rate limiting.

Webhook auto-rebuild - GitHub webhook listener triggers automatic rebuild on push. Configurable per repo. Async rebuild with audit logging.

AI-powered failure investigation - When a deployment fails, Qwen analyzes the error and produces a problem/solution report. Rule-based fallback for 8 error types when Qwen is unavailable. Reports stored and displayed in modal with hide/reveal.

Hide/reveal for secrets - SecretField and SecretText components on settings page and deployment page. Eye icon toggles visibility. Copy button. Webhook URL masked by default.

15 frontend pages - Dashboard, Agent, Analytics, Approvals, Containers, Decisions, Deployments, Files, Memory, Monitoring, Remote, Security, Settings, Terminal, Topology.

Persistent memory (7 layers) - M1 (raw events), M2 (observations), M3 (SOPs), M4 (user prefs), M5 (patterns), M6 (errors), M7 (context). Stored in Postgres.

Decision pipeline - DRE (Deep Research Engine), DREV (pairwise verification), CRDS (cascade reaction scoring), DQS (decision quality score), certainty pipeline with confidence and risk assessment.

Alibaba Cloud integration - ECS instance metadata via Alibaba SDK. Code in backend/src/utils/alibaba.js.

3.3 Deployment Bug Handling - How Are File Bugs Managed?

The user asked: when deploying from GitHub, if there are bugs in the files, how is it managed? Is it sent back or self-managed by AI? Does it edit the files? Does it need approval?

GAP 8: AI does NOT edit files in deployed repos (MAJOR)

Current behavior: When a deployment fails, the system generates an AI investigation report that describes the problem and suggests solutions. But the AI does not actually edit the files in the repo to fix the bugs. It only produces a text report.

This is a significant gap. In a real DevOps autopilot, the agent should be able to:

  1. Identify the specific file and line causing the build failure
  2. Propose a fix (patch/diff)
  3. Get human approval before applying the fix
  4. Apply the fix to the cloned repo
  5. Rebuild and verify
  6. If the fix works, optionally create a PR back to the GitHub repo

Action needed: Add a file-editing capability to the deploy engine. When AI investigation identifies a fixable error, generate a patch, show it to the user for approval, apply it, and rebuild. This would be a major differentiator for the judges.

GAP 9: No stack-specific build error handling (MODERATE)

The deploy engine detects the stack type but does not have stack-specific error handling. For example:

  • HTML/Static: No build step, so errors are minimal. Works.
  • JavaScript/Node: npm install or npm run build errors are caught but not parsed for specific fixable issues.
  • Python: pip install errors or import errors are caught but not parsed.
  • Go: go build errors are caught but not parsed.

The AI investigation classifies errors by type (dependency, code, database, etc.) but does not have stack-specific parsers that extract the exact file and line number.

Action needed: Add stack-specific error parsers that extract file path, line number, and error message from build output. Feed this to the AI for more targeted fixes.

3.4 Compliance and Regulatory Protocol

GAP 10: No compliance or regulatory protocol (MAJOR)

The system has a 7-layer SAF for security, but it does not have any compliance or regulatory framework. In a production DevOps system, compliance means:

  • Data retention policies: How long are logs kept? Are they automatically purged?
  • PII handling: Does the system handle personally identifiable information? How is it protected?
  • Audit trail requirements: Are audit logs tamper-proof? Can they be exported for compliance reviews?
  • Access control: Beyond admin/operator roles, are there RBAC policies? Session management? Password policies?
  • Data residency: Where is data stored? Does it comply with GDPR/SOC2/etc.?
  • Incident response: Is there a formal incident response plan? Escalation procedures?

The current SAF has L5 (Immutable Logging) and L7 (Governance) but these are basic checks, not a full compliance framework.

Action needed: Add a compliance page or section that documents: data retention policy, audit log export, access control matrix, incident response procedure. Even a documentation page would help. Implementing actual data retention and log export would be better.

3.5 Security Protocol Gaps

GAP 11: No authentication on the API (MODERATE)

The backend API has no authentication middleware. Anyone who can reach port 3000 can call any endpoint, including deploying apps, running commands, and changing settings. The SAF checks user role but the user object is hardcoded as {username: "api", role: "admin"} in most routes.

Action needed: Add JWT authentication middleware. At minimum, protect deployment and settings endpoints with a token. For the hackathon demo, a simple API key header would suffice.

GAP 12: No HTTPS (MINOR for hackathon)

The ECS serves HTTP on port 3000. No TLS/SSL. For a production system this is critical. For a hackathon demo, it is acceptable but judges may note it.

GAP 13: Docker socket mounted in backend container (SECURITY RISK)

The docker-compose.prod.yml mounts /var/run/docker.sock into the backend container. This gives the backend full root access to the host Docker daemon. If the backend is compromised, the entire host is compromised.

Action needed: Document this as a known trade-off for the hackathon. In production, use a Docker proxy or separate the Docker management into a privileged sidecar.

6.6 Known Issues and Bugs

  • High CPU on ECS: Monitor was polling every 30s with expensive process/network enumeration. Fixed to 60s with heavy ops every 5th tick. Backend container now CPU-limited to 0.5 cores.
  • Frontend build hangs on ECS: TypeScript type checking consumes too much memory. Fixed by disabling TS/ESLint checks during Docker build. Types are still checked in dev mode.
  • Docker Compose v1 on ECS: ECS has docker-compose (hyphenated), not docker compose (v2). All commands must use the hyphenated form.
  • Webhook configs in memory: Webhook configs and deployment reports are stored in-memory (Maps/arrays). They will be lost on backend restart. For production, move to Postgres.
  • Secrets on settings page show empty: The settings page reads process.env.NEXT_PUBLIC_* which are frontend-exposed vars. Real secrets are backend-only and not exposed to the frontend. This is correct behavior but the UI shows empty fields which looks like a bug.

9. Devpost Submission Description

Copy and paste this into the Devpost text description field:

ALTHR Autopilot - AI-Native Server Operations Agent

ALTHR Autopilot is an AI agent that automates server operations end-to-end. It monitors Linux servers, detects anomalies, diagnoses root causes using Qwen Cloud, proposes remediation actions, and executes them with human-in-the-loop checkpoints at critical decision points. It also deploys applications from GitHub repositories with automatic stack detection, Dockerfile generation, and AI-powered failure investigation.

How it uses Qwen Cloud:

The system integrates with DashScope API (Qwen Cloud) for multiple AI functions: anomaly diagnosis with streaming reasoning, deployment failure investigation, file fix proposals for broken builds, and natural language command processing. It uses model rotation across qwen-turbo, qwen-plus, and qwen-max with token tracking, budget enforcement, and a kill switch. Guardrails include caching, rate limiting, and prompt optimization to minimize token usage.

Key features:

  • 7-Layer Security Framework (SAF): Every agent action passes through 7 security layers: asset classification, identity verification, network segmentation, command whitelist enforcement, immutable logging, blast radius containment, and governance with human approval routing.
  • Decision Intelligence Pipeline: Deep Research Engine (DRE) generates candidate solutions, DREV does pairwise verification, CRDS scores cascade reactions, and a certainty pipeline assesses confidence and risk before execution.
  • Continuous Monitoring: Tracks CPU, RAM, disk, network bandwidth, network latency, processes, ports, OS info, and Docker container health. Detects anomalies and triggers AI diagnosis with real-time reasoning streamed to the dashboard.
  • Multi-Stack Deployment Engine: Clones GitHub repos, detects stack type (Node.js, Next.js, Python, FastAPI, Go, PHP, static HTML), generates Dockerfiles, builds images, runs containers, and performs health checks.
  • AI-Powered Failure Investigation: When a deployment fails, Qwen analyzes the error output and generates a problem-solution report. If the AI identifies a specific fixable file, it proposes a patch that requires human approval before applying and rebuilding.
  • GitHub Webhook Auto-Rebuild: Configurable webhooks trigger automatic rebuilds when code is pushed to GitHub.
  • 7-Layer Persistent Memory: Raw events, observations, SOPs (with learning loop that skips AI when a known fix exists), user preferences, patterns, error memory, and context window. Stored in PostgreSQL.
  • Human-in-the-Loop: High-risk or low-confidence actions create pending approvals. The dashboard shows them with the proposed plan, confidence score, and risk level. Humans can approve or reject.
  • Compliance Framework: Immutable audit trail, command whitelist, secret management with hide/reveal UI, API key authentication, data residency documentation, and incident response procedures.

Deployment: Running on Alibaba Cloud ECS with Docker Compose (4 containers: PostgreSQL, Redis, backend, frontend). Live at http://47.84.106.210:3001.

Alibaba Cloud proof: https://github.com/298althr/QWENCLOUD/blob/track4/backend/src/utils/alibaba.js

Tech stack: Qwen Cloud (DashScope API), Node.js, Express, Socket.io, PostgreSQL with pgvector, Redis, Next.js 14, TypeScript, Tailwind CSS, Docker Compose, Alibaba Cloud ECS.
